# 完善产品需求

在用户确认「要写功能」且**没有**现成 UI 图时使用。禁止未确认需求就出预览图或写业务代码。

企业后台 / B2B / 工作台：读完本文后叠加 `enterprise.md`。

## 输入

- 用户原始产品描述
- 已创建项目的蓝图与开关（`.meridian/project.json`，若有）
- 用户补充的约束（端、角色、是否要登录等）

描述含糊时先问最多 5 个封闭问题，不要一次抛问卷。

## 必须产出的章节

写入 `<project>/docs/requirements.md`，缺一节不算完成：

1. **目标用户**：谁、在什么场景打开、成功标准是什么
2. **信息架构**：一级导航 + 每个入口对应的页面/状态
3. **主流程**：从打开应用到完成一件 P0 任务的步骤（含分支）
4. **状态**：空态 / 加载 / 错误 / 无权限 各写清文案与下一步
5. **P0 验收**：可勾选清单，必须能在一到两个页面内演示
6. **明确不做**：本轮不实现的能力（P1/P2），避免范围膨胀

## 保守规则

- 描述没提的能力不要写进 P0（登录、支付、审批、多租户、i18n 都算）
- 脚手架已有分层：需求里写「落在 engine / ui / pages」，不要要求新框架
- Mock 数据即可；不要把后端、数据库、SSO 写成 P0，除非用户坚持
- 有 UI 图时：按图补全上述章节，冲突处以用户确认为准

## 确认

把完整需求贴给用户，问「按这份写预览图吗？」。未确认不得进入 `ui-preview.md`。
